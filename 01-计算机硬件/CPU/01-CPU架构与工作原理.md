# CPU 架构与工作原理

> **一句话结论**：现代 CPU 的性能不来自「跑得快」，而来自**同一时刻在偷偷做几十件事**——流水线、乱序、预测、缓存，全都是为了让执行单元不闲着。
> **数据基准**：2026-08 ｜ **难度**：进阶 ｜ **前置**：无

---

## 1. 为什么要搞懂这个

因为参数表会骗人。

同频率、同核心数的两颗 CPU，性能可以差 40%。差在哪？差在 IPC（每周期指令数），而 IPC 由微架构决定。不理解流水线和缓存，你就只能靠跑分选 U，也解释不了为什么自己写的循环换个数组布局就快了三倍。

## 2. 从指令到结果：一条指令的一生

### 2.1 经典五级流水线

最简化的模型（RISC 教科书版）：

```
      取指      译码      执行      访存      写回
     ┌────┐   ┌────┐   ┌────┐   ┌────┐   ┌────┐
     │ IF │ → │ ID │ → │ EX │ → │MEM │ → │ WB │
     └────┘   └────┘   └────┘   └────┘   └────┘
       ↑
   从 L1i 缓存取指令
```

不用流水线：一条指令走完 5 步才开始下一条 → 5 周期/指令。
用流水线：像洗衣店，洗衣机、烘干机、折叠台同时工作 → 理想情况 1 周期/指令。

**关键洞察**：流水线不缩短单条指令的延迟（还是 5 个周期才出结果），只提升吞吐。这个「延迟 vs 吞吐」的区分会在整个硬件领域反复出现（见 [总线笔记](../总线/01-总线原理与分类.md)）。

### 2.2 现代 x86 的真实流水线

现代高性能核心是 **14–20 级**流水线，而且前后端分离：

```
┌─────────────────── 前端 Front-end ───────────────────┐
│  分支预测器 → L1i 取指 → 指令长度解码 → 微码译码       │
│                              ↓                        │
│                    x86 指令 → μop（微操作）            │
│                              ↓                        │
│                       μop Cache（跳过译码）            │
└──────────────────────────┬───────────────────────────┘
                           ↓  每周期发射 6–8 个 μop
┌─────────────────── 后端 Back-end ────────────────────┐
│  重命名 → 重排序缓冲 ROB → 调度器 → 执行端口           │
│                                    ├─ ALU ×4          │
│                                    ├─ AGU ×2（地址）  │
│                                    ├─ FP/SIMD ×2–3    │
│                                    └─ Load/Store      │
│                              ↓                        │
│                        按序退休（Retire）              │
└───────────────────────────────────────────────────────┘
```

**为什么 x86 要翻译成 μop**：x86 指令长度可变（1–15 字节）、语义复杂（一条 `ADD [mem], reg` 包含读-算-写三件事）。把它拆成定长、单一职责的 μop 之后，后端就可以用类 RISC 的方式高效调度。这也是「x86 vs ARM 谁更高效」这个争论在 2026 年基本失去意义的原因——**译码开销在总功耗里占比已经很小，架构差异远不如工艺和设计投入重要**。

### 2.3 乱序执行（Out-of-Order, OoO）

程序写的顺序 ≠ 执行的顺序 ≠ 结果提交的顺序。

```c
a = ptr[i];      // ① 缓存未命中，要等 200 周期
b = x + y;       // ② 和 ① 无关
c = b * 2;       // ③ 依赖 ②
```

顺序执行：卡在 ① 上，②③ 干等 200 周期。
乱序执行：① 发出访存请求后挂起，②③ 立刻执行，等 ① 数据回来再补上。

实现三件套：

| 机制 | 作用 | 类比 |
| --- | --- | --- |
| **寄存器重命名** | 消除「假依赖」（WAR/WAW），物理寄存器远多于架构寄存器 | 同名变量换个马甲，互不干扰 |
| **重排序缓冲（ROB）** | 记录指令原始顺序，保证**按序退休** | 排队叫号，谁先办完都行，但按号发结果 |
| **保留站 / 调度器** | 操作数就绪就发射 | 谁的菜齐了谁先下锅 |

ROB 深度是衡量后端能力的关键指标：现代大核 ROB 在 **500–630 项**量级，意味着可以「同时在飞」几百条指令。

## 3. 缓存层级：真正的性能主战场

### 3.1 为什么需要缓存

CPU 快，内存慢，而且差距越拉越大（**内存墙**）。典型延迟阶梯：

| 层级 | 典型容量 | 访问延迟 | 换算成「人类时间」 |
| --- | --- | --- | --- |
| 寄存器 | ~1 KB | 0 周期 | 立刻 |
| L1 数据缓存 | 32–128 KB / 核 | 4–5 周期 | 1 秒 |
| L2 缓存 | 1–3 MB / 核 | 14–20 周期 | 4 秒 |
| L3 缓存（共享） | 24–128 MB | 40–70 周期 | 15 秒 |
| 内存 DDR5 | 16–192 GB | 70–100 ns（≈250 周期） | 1 分钟 |
| NVMe SSD | TB 级 | 20–80 μs | 6 小时 |
| 机械硬盘 | TB 级 | 5–10 ms | 1 个月 |

> 把这张表背下来，你就能凭直觉判断一段代码为什么慢。

### 3.2 缓存行与局部性

缓存的最小单位是 **缓存行（Cache Line）= 64 字节**（x86 与主流 ARM 均为 64B，苹果 M 系列部分为 128B）。

读一个 `int`（4 字节），实际搬了 64 字节进来。所以：

```c
// 快：行优先遍历，每 16 个 int 才触发一次 miss
for (i = 0; i < N; i++)
    for (j = 0; j < N; j++) sum += a[i][j];

// 慢：列优先，几乎每次都 miss，可能慢 5–10 倍
for (j = 0; j < N; j++)
    for (i = 0; i < N; i++) sum += a[i][j];
```

**伪共享（False Sharing）**：两个线程分别写同一缓存行里的不同变量，硬件层面仍会互相踢来踢去（缓存一致性协议），性能暴跌。解决办法是把热点变量按 64 字节对齐填充。

### 3.3 缓存一致性：MESI

多核共享内存，必须保证「A 核改了，B 核看到的不是旧值」。MESI 协议给每个缓存行打四种状态标签：

| 状态 | 含义 | 能否直接写 |
| --- | --- | --- |
| **M** Modified | 我改过，且只有我有，内存里是旧的 | 能 |
| **E** Exclusive | 只有我有，和内存一致 | 能（转 M） |
| **S** Shared | 多个核都有，只读 | 不能，要先广播使其他核失效 |
| **I** Invalid | 无效 | 不能，要先取 |

AMD 用 MOESI（多一个 Owned 状态，减少写回内存的次数），Intel 用 MESIF（多一个 Forward，指定一个核负责转发）。

**实际影响**：多线程程序里对共享变量的原子操作代价高，不是因为「原子」本身，而是因为它触发了跨核的缓存行搬运。

## 4. 分支预测：赌对了白赚，赌错了重罚

流水线 18 级，遇到 `if` 时还不知道走哪边，怎么办？**猜**。

- 猜对：无缝继续，零代价。
- 猜错：清空流水线，**罚 15–20 个周期**。

现代预测器（TAGE / 感知机类）准确率 **95–99%**。但注意这个数字的残酷之处：

```
准确率 99% 时：平均惩罚 = 0.01 × 18 ≈ 0.18 周期/分支
准确率 90% 时：平均惩罚 = 0.10 × 18 ≈ 1.8 周期/分支   ← 差了 10 倍
```

对随机数据做 `if (x > threshold)` 判断是预测器的噩梦。这就是「排序后的数组遍历比乱序数组快」这个经典面试题的答案。

**无分支编程**：用条件传送（`CMOV`）、位运算、查表替代分支，在数据不可预测时收益明显。

## 5. 并行的四个层次

| 层次 | 英文 | 手段 | 谁负责 |
| --- | --- | --- | --- |
| 指令级并行 | ILP | 流水线、超标量、乱序 | 硬件自动 |
| 数据级并行 | DLP | SIMD（SSE/AVX/NEON/SVE） | 编译器 + 手写 intrinsic |
| 线程级并行 | TLP | 多核、SMT/超线程 | OS + 程序员 |
| 请求级并行 | RLP | 多机、集群 | 架构设计 |

### SIMD 指令集演进

| 指令集 | 位宽 | 出现时间 | 说明 |
| --- | --- | --- | --- |
| MMX / SSE | 64 / 128 bit | 1997 / 1999 | 上古时代 |
| AVX / AVX2 | 256 bit | 2011 / 2013 | 当前兼容性最好的基线 |
| AVX-512 | 512 bit | 2016 | 分裂成十几个子集，降频问题曾饱受诟病 |
| **AVX10** | 128/256/512 | 2023 起 | Intel 用来统一混乱局面：大小核都支持同一套语义，512 位可选 |
| ARM NEON | 128 bit | — | ARM 基线 |
| ARM SVE / SVE2 | 可变长（128–2048） | — | 「向量长度无关」编程，代码不用为位宽重写 |

### SMT / 超线程

一个物理核伪装成两个逻辑核，共享执行单元，独立维护架构状态（寄存器、PC）。

- **收益**：当一个线程因缓存未命中停顿时，另一个线程顶上，填满执行端口。典型提升 **15–30%**。
- **代价**：两个线程抢 L1/L2 缓存，可能互相拖累；侧信道安全风险（Spectre 类漏洞）。
- **趋势**：Intel 在 Arrow Lake（Core Ultra 200S）上**取消了超线程**，理由是在混合架构下，加 E-core 比加 SMT 更划算——同样的芯片面积，E-core 给的多线程收益更高。AMD 目前仍保留 SMT。

## 6. 混合架构：大核 + 小核

从 Alder Lake（12 代酷睿）开始，x86 桌面进入混合时代。

| | P-core（性能核） | E-core（能效核） |
| --- | --- | --- |
| 目标 | 低延迟、高单线程 | 高吞吐、高密度 |
| 流水线 | 深、宽、大 ROB | 相对精简 |
| 面积 | 1× | 约 1/4 |
| 频率 | 高（5.5 GHz+） | 中（3.5–4.5 GHz） |
| 缓存 | 独享大 L2 | 4 核共享一块 L2（cluster） |

**调度是难点**：OS 必须知道哪个线程该去大核。Intel 的解法是 **Thread Director**——CPU 内部硬件实时统计每个线程的指令混合特征（是不是在跑 AVX？是不是在自旋等待？），把提示喂给操作系统调度器。

早期翻车案例：Windows 10 不认 Thread Director，把游戏主线程丢到 E-core，帧数暴跌；某些 DRM 把 E-core 当成作弊硬件直接拒绝启动。这类问题在 Windows 11 + 新 BIOS 上基本解决。

## 7. 常见误区

- ❌ **「主频高就快」** → ✅ 性能 ≈ 频率 × IPC × 核心利用率。跨架构比频率毫无意义（见 [参数详解](./02-CPU参数详解与分类对比.md)）。
- ❌ **「核心越多越好」** → ✅ 受阿姆达尔定律限制。串行占比 10% 的程序，无限核心也只能加速 10 倍。游戏通常只吃 6–8 核。
- ❌ **「缓存越大越好」** → ✅ 缓存增大会**增加访问延迟**。L3 从 32MB 加到 128MB，命中率涨一点点，延迟涨不少。3D V-Cache 之所以能成，是因为它靠堆叠把大容量放在了物理上极近的位置。
- ❌ **「x86 天生比 ARM 费电」** → ✅ 主要差距来自工艺节点、设计目标（服务器 vs 手机）和功耗墙设定，指令集本身的影响在现代设计中占比很小。
- ❌ **「超线程 = 两个核」** → ✅ 是一个核的执行资源被两个线程分时复用，收益 15–30%，不是 100%。
