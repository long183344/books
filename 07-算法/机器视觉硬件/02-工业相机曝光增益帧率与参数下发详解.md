## 一句话结论

> **增益 = 数字时代的 ISO，放大信号也放大噪声，暗部尤甚，所以"先加光、后加曝、最后加增益"是铁律；帧率由"曝光时间 + 图像读出时间"共同决定，读出时间硬件固定、靠 ROI 才能缩短；而"测曝光切换最高帧率"本质是测相机逐帧改参数的稳定极限——必须同时满足"无丢帧 + 每帧曝光真生效"，否则只是假帧率（指令发了，相机寄存器还没更新就开始采图）。**

## 1. 增益（Gain）、ISO 与噪点的关系（详解）

### 1.1 增益到底是什么

增益（Gain）是相机对**传感器输出信号**的放大倍数，分两种：

| 类型 | 作用位置 | 特点 |
| --- | --- | --- |
| **模拟增益** | 传感器输出后、ADC 之前 | 放大模拟电压；放得越大，本底噪声和读出噪声一起被放大 |
| **数字增益** | ADC 之后（数字域） | 直接对数字像素值乘系数；不增加真实信息，只提亮，噪点更"硬" |

无论哪种，增益的**唯一目的**是：在光照不足时把微弱信号拉到可用亮度，代价是噪声同步被放大。

### 1.2 数码相机的 ISO 就是这里的增益

- **ISO 数值 = 增益档位**。增大 ISO，本质是**提高感光器件对光的灵敏度**（等效于把信号放大更多倍）。
- 所以"高 ISO 拍夜景更亮"和"工业相机加大 Gain 更亮"是**同一件事**。

### 1.3 噪点规律（必须记住）

```
增益 越小  ──▶  噪点 越小  （画面干净，但弱光下偏暗）
增益 越大  ──▶  噪点 越多  （尤其暗处，亮斑/彩色杂点爆发）
```

**原理**：高感光度对弱光灵敏，**同时对噪声信号也灵敏**。信号被放大的同时，传感器的本底热噪声、读出噪声也被同比例放大，于是**信噪比（SNR）下降** → 肉眼看到噪点变多。

> 暗处噪点最明显，是因为暗区信号本就微弱，放大后"信号/噪声"比值最低，噪声相对最突出。

### 1.4 降噪的边界

- 图像软件（HALCON 的 `mean_image` / `median_image`、OpenCV 的 `fastNlMeansDenoising` 等）可以**减轻或去除**噪点；
- 但降噪必然**损失细节/边缘**，且无法找回被噪声淹没的真实信号——**源头控增益才是正道**。

### 1.5 铁律（衔接上篇）

再次强调参数优先级：

```
先加光（打强光/频闪）  →  再加曝光（拉长曝光时间）  →  最后才加增益（逼不得已才动）
```

增益是**最后的手段**，不是首选。

## 2. 曝光时间（Exposure Time）

| 属性 | 说明 |
| --- | --- |
| 定义 | 传感器感光的时间长度 |
| 可控性 | **可手动调节**（相机参数 `ExposureTime`） |
| 与亮度的关系 | 曝光越长 → 进光越多 → 画面越亮 |
| 与运动的矛盾 | 曝光越长 → 运动物体拖影越严重 |

### 2.1 拖影公式（飞拍/产线必算）

```
物体位移 = 物体速度 × 曝光时间
```

实例：

| 场景 | 速度 | 曝光 | 拖影 | 评价 |
| --- | --- | --- | --- | --- |
| 产线产品 | 1 m/s | 10 ms | 10 mm | 严重模糊，不可用 |
| 飞拍（博客例） | 500 mm/s | 100 µs | 0.05 mm ≈ 1 像素 | 通常可接受 |
| 飞拍（更严） | 500 mm/s | 20 µs | 0.01 mm | 几乎无拖影 |

### 2.2 冻住运动物体的正确姿势

要拍清运动物体，**不能靠长曝光**（会糊），而必须：

1. **短曝光**（冻结运动，见上表）；
2. **配合强光补光 / 频闪光源（Strobe）**——短曝光下进光少，必须靠瞬间强光把亮度补回来。

> 这就是为什么飞拍系统里**光源往往是最大瓶颈**：曝光压到 100µs 甚至更短时，常亮光源根本不够亮，必须用相机 IO 输出的 Strobe 信号驱动频闪灯在曝光瞬间爆亮。

## 3. 帧率（FPS）的本质与公式

### 3.1 核心公式

```
帧率（fps）        = 每秒能拍多少张图
单帧总耗时        = 曝光时间 + 图像读出时间
```

**每拍一张完整的图，核心就这两步**：

| 步骤 | 名称 | 是否可调 | 决定因素 |
| --- | --- | --- | --- |
| ① | **曝光时间** | ✅ 可手动调节 | 你设多少就是多少 |
| ② | **图像读出时间** | ❌ 基本固定 | 相机硬件、分辨率、ROI 裁剪决定，你改不了（除非改分辨率/ROI/像素格式） |

### 3.2 两条 regime（决定帧率由谁主导）

```
┌─ 曝光时间 ＜ 读出时间 ─┐
│  帧率由"读出速度"决定，基本维持最高帧率。
│  例：曝光从 1µs 调到 5000µs(5ms)，帧率大概率仍 >150fps。
│
└─ 曝光时间 ＞ 读出时间 ─┐
   帧率由"曝光时间"主导，曝光越长，帧率越低。
   （曝光 5ms → 最多 ~200fps 上限；曝光 50ms → 最多 ~20fps）
```

> 直觉：曝光很短时，相机"等"读出的时间占比最大，所以帧率卡在读出速度上；曝光很长时，"感光"本身成了最慢的一环，帧率被曝光拖死。

### 3.3 标称帧率 ≠ 实测帧率

相机手册标的最高帧率通常是**理想条件**（最小 ROI / 特定像素格式 / 无触发开销）。实际还要扣掉：

- 图像**传输**耗时（接口带宽，见上篇 GigE/USB3 带宽公式）；
- **触发**开销（触发模式下的响应延迟）；
- **算法处理**耗时（取流后你的视觉算法占用）。

所以"调短曝光帧率没变化"是正常现象——你可能一直处在 regime①（读出受限），而不是曝光受限。

## 4. 突破帧率上限：ROI 裁剪

| 手段 | 原理 | 副作用 |
| --- | --- | --- |
| **裁剪 ROI**（只取需检测区域） | 传感器需读出的数据量 ↓ → 读出时间 ↓ → 最高帧率 ↑ | 视野变小，需重新标定 |
| 降低分辨率 | 同上，读出像素更少 | 细节损失 |
| 改用 Mono8（灰度 8bit） | 单像素字节数从 3(RGB)/2(12bit) 降到 1 | 丢失彩色/高位深 |
| 提高接口带宽（GigE→10GigE） | 传输不再是瓶颈 | 成本上升 |

**关键结论**：`单帧总耗时` 里的"读出时间"你改不了，但**ROI 能改它**——这是现场提升帧率最直接、零成本的手段。博客里飞拍算不过来帧率时，第一建议就是"降分辨率 / 开 ROI"。

## 5. 参数下发耗时与"假帧率"陷阱（结合海康实战）

### 5.1 参数下发是有"耗时"的

工业相机的曝光、增益等参数，是通过 SDK 命令**写入相机内部寄存器**的。这条链路有真实延迟：

```
上位机 SetExposureTime(1000)
   │  (命令经 USB/网口下发，ms 级)
   ▼
相机固件接收命令，写入曝光寄存器
   │  (固件处理 + 应用到下一帧，再耗一点时间)
   ▼
下一帧开始按新曝光值感光
```

> 博客《海康相机触发机制详解》把软触发拆成"**命令下发 → 相机响应 → 图像回传**"三段，并指出**前两段就是延迟和抖动的主要来源**；还强调"软触发命令不能发太快，超出相机最大帧率后后面的触发命令会被丢弃"——这正是"下发 ≠ 立即生效"的工程印证。

### 5.2 "测曝光切换最高帧率"到底在测什么

本质：**测相机"逐帧更换曝光参数的稳定工作极限"**。

典型场景：你想在高速产线上**逐帧动态改曝光**（比如交替拍亮/暗两种工件），需要知道相机一秒能稳定切换多少次。

### 5.3 假帧率陷阱（重点）

> ⚠️ **不能只看帧率数字！** 必须同时满足两个条件，否则测出来的是**假帧率**：
> 1. **无丢帧**（实际出图数 = 期望帧数）；
> 2. **每帧曝光都真正生效**（相机寄存器已更新，不是在用旧值采图）。

错误现象：指令下发了，但相机**还没来得及更新曝光寄存器就开始采图** → 你以为在测"切换帧率"，实际采到的还是旧曝光，帧率数字再高也是假的。

### 5.4 正确测法（checklist）

1. **制造可分辨差异**：用强补光 + 短曝光，让不同曝光值对应的图像亮度**肉眼/直方图可区分**。
2. **逐帧回读确认**：每帧后调用 `GetExposureTime()` 读回实际生效值（或直接分析该帧亮度直方图），确认参数已真正切换。
3. **统计丢帧**：对比"期望帧数"与"实际收到帧数"，有落差即说明超频/命令被丢弃。
4. **取真实上限**：在满足"无丢帧 + 每帧曝光真生效"的前提下，逐步拉高切换频率，取最大稳定值。

```text
伪代码（思路，非具体 SDK）：
for each frame:
    set_exposure(next_value)        // 下发新曝光
    wait_until_applied()            // 关键：等寄存器生效（或读回确认）
    grab_one_frame()                // 采图
    actual = get_exposure()         // 回读，验证真生效
    assert actual == next_value     // 不生效就说明到极限了
    record_no_drop()                // 统计丢帧
```

> 工程实践：海康等相机通常在 `SetXXX` 后**读回 `GetXXX` 确认**，或在**触发模式**下用"下发 → 等待 → 触发采图"的固定时序保证顺序，避免"命令追着采图跑"。

## 6. 实战调试清单（曝光 / 增益 / 帧率 / 参数下发）

| 步骤 | 动作 | 检查点 |
| --- | --- | --- |
| 1 | 先打够光（常亮 + 必要时频闪） | 不动增益也能看清 |
| 2 | 设短曝光冻运动 | 拖影 < 1 像素（用 `位移=速度×曝光` 算） |
| 3 | 亮度仍不足才加增益 | 增益尽量低，暗部噪点可接受 |
| 4 | 帧率不够先开 ROI / 降分辨率 | 读出时间 ↓，最高帧率 ↑ |
| 5 | 动态改参数前先验证"下发即生效" | 回读 `GetExposureTime` 确认 |
| 6 | 测切换帧率时统计丢帧 | 实际帧数 = 期望帧数 |
| 7 | 软触发别连发 | 等回调收到图再发下一条，否则命令被丢弃 |
| 8 | 运动场景用硬触发 / 飞拍 | 位置信号直连相机，微秒级稳定，别用软件延时 |

## 7. 与上篇的衔接（参数铁三角 + 触发）

- **参数铁三角**（上篇 [`01-工业相机详解`](./01-工业相机详解.md)）：**光 → 曝光 → 增益** 的优先级，本篇用"增益=ISO、噪点机制"把它坐实。
- **触发方式**（上篇 + 博客）：内触发 / 外触发(硬触发) / 软触发。本篇第 5 节的"假帧率"问题，在**软触发连续发命令**时最易出现（命令超帧率被丢）；而**硬触发**因微秒级稳定、由硬件位置信号驱动，是飞拍/动态改参数的可靠底座。
- **帧率公式**：上篇讲"帧率受曝光+读出+带宽三重限制"，本篇把"曝光+读出"拆成 regime①/②，并补上"ROI 缩短读出时间"这把钥匙。

## 8. 术语速查

| 术语 | 一句话 |
| --- | --- |
| 增益 Gain | 传感器输出信号放大倍数；= 数码相机 ISO |
| ISO | 增益档位；增大 = 提高感光灵敏度，同时放大噪声 |
| 噪点 | 增益/高 ISO 放大本底与读出噪声的产物，暗部最明显 |
| 曝光时间 | 传感器感光时长，可手动调；越长越亮但越易拖影 |
| 拖影 | 运动物体在曝光期间的位移，`位移=速度×曝光` |
| 帧率 fps | 每秒出图张数 = 1 / (曝光时间 + 读出时间) |
| 读出时间 | 传感器把图像传出所需时间，硬件/分辨率/ROI 决定，基本固定 |
| ROI | 感兴趣区域裁剪，减少读出数据量 → 提高帧率 |
| 参数下发耗时 | SDK 写相机寄存器有 ms 级延迟，下发 ≠ 立即生效 |
| 假帧率 | 只数帧率数字、未验证"无丢帧+每帧曝光真生效"测出的虚高值 |

## 9. 文字脑图（总结）

```
工业相机成像参数（扩展篇）
├─ 增益 = ISO
│   ├─ 放大信号，也放大噪声 → 暗部噪点最多
│   ├─ 铁律：先光 → 后曝 → 最后增益
│   └─ 降噪只能补救，源头控增益才正道
├─ 曝光时间
│   ├─ 越长越亮，但运动拖影：位移 = 速度 × 曝光
│   └─ 冻运动：短曝光 + 频闪强光
├─ 帧率 = 1 / (曝光 + 读出)
│   ├─ 曝光 < 读出 → 帧率卡在读出（维持最高）
│   ├─ 曝光 > 读出 → 帧率被曝光拖死
│   └─ ROI/降分辨率 → 缩短读出 → 破帧率上限
└─ 参数下发 ≠ 立即生效
    ├─ 假帧率陷阱：只数帧率，没验证无丢帧+每帧真生效
    └─ 正确测法：可分辨差异 + 逐帧回读 + 统计丢帧
```

## 10. 快速决策表

| 你遇到的现象 | 优先排查 |
| --- | --- |
| 画面暗、噪点多 | 先加光/加曝，最后才加增益；增益别超必要值 |
| 运动物体模糊/拖影 | 缩短曝光 + 加强光；用 `位移=速度×曝光` 反算允许最大曝光 |
| 帧率上不去 | 看是否 ROI 太小/分辨率太高（读出受限）；或曝光已超读出 |
| 标称 150fps 实测只有几十 | 大概率处在读出受限 regime①，或带宽/触发开销没算进去 |
| 动态改曝光测出的"帧率"不稳 | 假帧率！回读 `GetExposureTime` + 统计丢帧后再下结论 |
| 软触发连续发命令丢图 | 超最大帧率被丢弃，等回调收到图再发下一条 |
